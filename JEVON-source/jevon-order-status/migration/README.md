# Миграции PostgreSQL

Все SQL-миграции и служебные операции БД общего проекта находятся в этой папке. Рабочий адаптер запросов приложения остаётся в `scripts/postgres-storage.mjs`.

## Развёртывание на сервере

Установите зависимости проекта, задайте `DATABASE_URL` в переменных окружения или `.env`:

```text
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/jevon
```

Из папки `jevon-order-status` выполните:

```sh
node migration/deploy.mjs
node migration/check-postgres.mjs
```

`deploy.mjs` создаёт БД, если её нет, и применяет все SQL-миграции. Для создания БД пользователь должен иметь право CREATEDB. Можно указать отдельную административную строку подключения `ADMIN_DATABASE_URL`; владельцем новой БД будет пользователь из `DATABASE_URL`. Учётные данные не храните в SQL-файлах или репозитории.

Если хостинг уже предоставил готовую БД и запрещает CREATE DATABASE, выполните только:

```sh
node migration/migrate.mjs
```

После подготовки схемы приложение запускается обычными командами `pnpm build` и `pnpm start`. Они выполняют подготовку настроек и первоначальный импорт существующего каталога. Если нужен отдельно первоначальный импорт SQLite/фотографий/каталога и начальных сотрудников, выполните `node migration/setup-postgres.mjs`. `deploy.mjs` сам по себе создаёт только базу и схему, без загрузки каталога или сотрудников.

Команды package.json: `db:create`, `db:migrate`, `db:deploy`, `db:setup`, `db:check`.

`db:prepare` (`node migration/prepare.mjs`) проверяет подключение к целевой БД, создаёт отсутствующую БД, применяет миграции и готовит первоначальные данные. `start.bat`, `pnpm dev`, `pnpm build` и `pnpm start` выполняют эту подготовку автоматически до запуска приложения, в том числе если порт 8080 уже занят. При неверном пароле или недоступности сервера запуск завершается с ошибкой; такие ошибки не считаются отсутствием БД. Служба PostgreSQL должна быть запущена.

## Новые изменения

1. Добавьте новый файл в `migration/sql`, например `0002_add_employee_email.sql`, затем `0003_...sql`.
2. Включите в этот файл все необходимые CREATE/ALTER/INDEX, ограничения и преобразования существующих данных.
3. Выполните `node migration/migrate.mjs`, проверьте результат и включите SQL-файл в ту же поставку, что и код приложения.
4. Уже применённые SQL-файлы не изменяйте и не удаляйте; исправления оформляйте следующей миграцией.

Порядок определяется номером имени файла. Выполнение и запись в `schema_migrations` происходят в одной транзакции с блокировкой от параллельных запусков. Ошибка откатывает всю текущую серию новых миграций. Не добавляйте в SQL-файлы свои BEGIN/COMMIT, CREATE DATABASE или операции вроде CREATE INDEX CONCURRENTLY, которые требуют выполнения вне транзакции. Контрольные суммы нормализуют окончания строк Windows/Linux.

`0001_initial_schema.sql` создаёт все таблицы нынешнего общего проекта. Файл совместим с существующей базой `jevon`: таблицы и данные сохраняются, миграция регистрируется при первом запуске нового механизма.

`legacy/sqlite/` содержит исходные миграции Cloudflare D1/SQLite и метаданные Drizzle; PostgreSQL runner их не применяет. Они сохранены для прежнего Cloudflare-профиля и истории.

## Портал отчётов

Миграция `0002_reports_auth.sql` добавляет персональные учётные записи, сессии и ограничение попыток входа. Прежние PIN-коды кабинетов сотрудников не предоставляют доступ к порталу отчётов.

Для первого администратора можно задать `REPORTS_ADMIN_LOGIN` (по умолчанию `admin`) и `REPORTS_ADMIN_PASSWORD` (12–128 символов) в окружении или `.env` до первоначального запуска. Если пароль не задан, генерируется случайный пароль, который записывается в исключённый из Git `.sites-runtime/reports-admin.json`. При следующих запусках существующие учётные записи и пароли не перезаписываются.

После `db:migrate` отдельно выполнить первоначальное создание администратора можно командой `node migration/seed-reports-admin.mjs`; обычный запуск приложения также выполняет его автоматически. Вход: `/reports/login`. Создание пользователей: `/reports/users`, доступно только администратору. Аналитики имеют доступ к отчётам, но не к списку или созданию пользователей. Пароли хранятся как scrypt-хеши с индивидуальной солью; в БД хранится только хеш случайного токена сессии. Сессия действует 8 часов и отзывается при выходе. На хостинге используйте HTTPS — production-cookie имеет флаг Secure.
